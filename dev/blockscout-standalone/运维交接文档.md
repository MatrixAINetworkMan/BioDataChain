# Blockscout 区块浏览器 —— 运维交接文档

> 交接对象：运维工程师
> 适用范围：独立部署的 Blockscout 区块浏览器（与链节点分机部署）
> 配套目录：`dev/blockscout-standalone/`
> 最后更新：2026-06-24（后端 optimism v11.2.0 自编译 / 前端 v2.8.0 自编译）

本文档面向运维，**不需要读源码即可上手操作**。涉及命令一律在
`dev/blockscout-standalone/` 目录下执行（除非另有说明）。

---

## 0. 一句话说明

这台机器只跑「区块浏览器」（Blockscout），用来给人浏览链上区块/交易/地址。
它本身**不出块、不存钱、不是链的一部分**，挂了不影响链运行，重装即可恢复（数据能从链
重新索引出来）。链节点在**另一台机器**。

## 1. 架构与依赖

```
┌──────────────────────────┐        RPC (HTTP/WS/trace)       ┌──────────────────────────┐
│  链机器（不归本机管）       │ ◀──────────────────────────────  │  本机：Blockscout 浏览器   │
│  op-geth  :9545 / :9546   │                                  │  8 个 docker 容器          │
│  op-node / op-batcher     │        L1 RPC :8545             │  + nginx 反代 + HTTPS      │
│  L1 geth  :8545（或独立机） │ ◀──────────────────────────────  │                            │
└──────────────────────────┘                                  └──────────────────────────┘
        提供数据源                                                    本机消费数据源
```

**强依赖（这些断了浏览器就不更新数据）**：
- 链机器的 L2 RPC：`9545`(HTTP) / `9546`(WS) —— 索引新区块
- L1 机器的 RPC：`8545` —— 索引跨链充提（deposit/withdrawal）

**本机内部 8 个容器**（一套 docker compose）：

| 容器名 | 作用 | 挂了的后果 |
|--------|------|-----------|
| `blockscout-backend` | 索引器 + API（核心） | 整站不更新、API 502 |
| `blockscout-frontend` | 网页界面 | 网页打不开 |
| `blockscout-stats` | 首页图表数据 | 首页「Daily transactions」为 0 |
| `blockscout-db` | 主数据库(Postgres) | backend 起不来 |
| `blockscout-stats-db` | 图表数据库(Postgres) | 图表服务起不来 |
| `blockscout-redis` | 缓存 | backend 起不来 |
| `blockscout-verifier` | 合约源码验证 | 验证合约功能失效（非核心） |
| `blockscout-sig-provider` | 函数签名解码 | 交易解码不全（非核心） |

## 3. 首次部署 / 重装

> 已部署的环境跳过本节。重装/迁移新机器时照做。

```bash
# 前置：装好 docker + 工具
sudo apt update && sudo apt install -y docker-compose-plugin jq gettext-base curl openssl

# 1. 拿到代码
git clone <仓库地址> && cd <仓库>/dev/blockscout-standalone

# 2. 品牌素材：assets/{logo.svg,icon.svg,logo512.png} 已随仓库自带，无需手动拷。
#    9 件套 favicon 会在第 4 步 install.sh 里自动生成（首次约 60 秒 + 拉
#    dpokidov/imagemagick 镜像 ~200MB）。要换品牌图：直接覆盖 assets/{logo.svg,icon.svg,logo512.png}
#    再跑 bash scripts/make-favicon.sh --force。

# 3. 配置（把所有 REPLACE_ME 改成真实值，详见第 8 节配置表）
cp .env.example .env
vim .env

# 4. 一键安装（自带连通性自检，1-3 分钟）
./install.sh

# 5. nginx 反代 + HTTPS
sudo cp nginx/blockscout.conf.example /etc/nginx/conf.d/<域名>.conf
sudo vim /etc/nginx/conf.d/<域名>.conf     # 改 server_name 和证书路径
sudo nginx -t && sudo systemctl reload nginx
```

> `install.sh` 是**幂等**的：改完 `.env` 重跑一次即可重新生效，不会重复出问题。

## 6. 升级 Blockscout（换版本）

⚠️ **后端 optimism 镜像 + 前端新版都必须自编译**（这是个坑，务必知道）：
Blockscout 自 v10 起停止发布公开 optimism 镜像，`ghcr.io/blockscout/blockscout-optimism` 永久停在
**9.0.2**（10/11 全 404），v10/v11 只在私有仓库 `blockscout-optimism-private`（外部拉不了）。optimism 是
编译期 chain type，通用 `blockscout` 镜像不能索引 OP 数据。所以后端上 v11 只能从源码编译。
**前端同理**：公开 `ghcr.io/blockscout/frontend` 永久停在 **v2.3.5**（`:latest` 也指它），v2.7/v2.8 只在
私有仓库 `frontend-private`，要新版前端也得自编译。stats / verifier / sig-provider 是公开镜像，照常用 tag/digest。

完整步骤（自编译 + 取 digest + 应用）见 `README.md`「升级 Blockscout」一节。要点：

```bash
# 1a. 自编译后端（约 4GB+ 内存、15–30 分钟）
git clone --depth 1 --branch v11.2.0 https://github.com/blockscout/blockscout.git && cd blockscout
DOCKER_BUILDKIT=1 docker build -f docker/Dockerfile \
  --build-arg CHAIN_TYPE=optimism --build-arg RELEASE_VERSION=11.2.0 \
  --build-arg BLOCKSCOUT_VERSION=v11.2.0 -t blockscout-optimism:11.2.0-local .

# 1b. 自编译前端（峰值 ~8GB 内存，不足先加 swap）
git clone --depth 1 --branch v2.8.0 https://github.com/blockscout/frontend frontend-src && cd frontend-src
docker build -f Dockerfile --build-arg GIT_TAG=v2.8.0 -t blockscout-frontend:2.8.0-local .

# 2. .env 里设 BLOCKSCOUT_BACKEND_IMAGE=blockscout-optimism:11.2.0-local
#    BLOCKSCOUT_FRONTEND_IMAGE=blockscout-frontend:2.8.0-local
#    stats:latest(≥2.16) / verifier:latest / sig:latest 取 digest 回填
vim .env

# 3. 升级前先备份（见第 7 节）

# 4. 应用：9.x→v11 无法直接迁移（v11 须装在 v10.1 上）→ 测试环境直接 greenfield 清库重装
docker compose --env-file .env down -v        # ⚠️ 清空索引，整条链重新同步
./install.sh                                   # 已支持本地镜像（pull --ignore-pull-failures）
```

> 同大版本内换补丁：直接改 `.env` 后 `./install.sh`，backend 启动会自动 `create_and_migrate()`。
> 5 个镜像变量：`BLOCKSCOUT_BACKEND_IMAGE / FRONTEND / STATS / VERIFIER / SIG_PROVIDER`。

## 7. 数据管理

### 7.1 数据存哪
docker 卷：`bs-db`（主库）、`bs-stats-db`（图表库）、`bs-redis`（缓存，可丢）。

### 7.2 备份
```bash
docker compose exec -T db pg_dump -U blockscout blockscout | gzip > backup-$(date +%F).sql.gz
```
建议放进 crontab 每日凌晨备份并同步到对象存储：
```cron
0 3 * * * cd /path/to/dev/blockscout-standalone && docker compose exec -T db pg_dump -U blockscout blockscout | gzip > /backups/bs-$(date +\%F).sql.gz
```

### 7.3 恢复
```bash
gunzip -c backup-2026-06-01.sql.gz | docker compose exec -T db psql -U blockscout blockscout
docker compose restart backend
```

### 7.4 磁盘清理
```bash
docker system prune -f      # 清无用镜像/容器（不动卷，安全）
docker compose logs --tail=0 -f   # 日志已限 20m×5/容器，一般无需手动清
```

| 变量 | 含义 | 取值来源 |
|------|------|---------|
| `BLOCKSCOUT_PUBLIC_URL` | 浏览器对外域名 | 本机域名，如 `https://scan.example.com` |

## 9. 故障处理手册

| 症状 | 排查 / 处理 |
|------|-------------|
| 网页打不开 / 502 | `docker compose ps` 看 frontend/backend；`docker compose logs backend`；`sudo nginx -t && systemctl reload nginx` |
| 区块号不涨（不索引新块） | 链 RPC 断了：`docker compose logs backend \| grep -i rpc`；在本机 `curl` 测 `L2_RPC_HTTP`（见下方自检命令）；确认链机器 op-geth 活着 |
| 首页 Daily transactions 一直 0 | `docker compose logs stats`；确认 `/stats-api/` 反代通 |
| 余额/交易显示滞后 | 高峰期索引滞后属正常，稍等会自动追上 |
| 充值/提现(deposit/withdrawal) 页空 | L1 RPC 断或合约地址错：`docker compose logs backend \| grep -i optimism`；检查 `L1_RPC` 和 4 个合约地址 |
| 交易页「Internal txns」标签为空（全站都空） | 内部交易索引器被关，或历史块未回填 —— 见 §9.1 专项处理 |
| 钱包「添加网络」报 RPC 无效 | `L2_RPC_PUBLIC_URL` 必须是 HTTPS |
| 实时不刷新需手动 F5 | nginx 缺 WebSocket map（见 nginx 配置文件顶部注释） |
| 容器反复重启 | `docker compose logs <容器名>` 看报错；磁盘满/内存不足是常见原因 |
| frontend 启动报 `error mounting ".../favicon.ico" ... not a directory` | `assets/favicon/` 下某文件缺失，docker bind-mount 自动 mkdir 出"伪目录"。一键修复：`docker compose stop frontend && docker compose rm -f frontend && bash scripts/make-favicon.sh --force && docker compose up -d frontend`（脚本会清理伪目录并重新生成完整 9 件套） |

**连通性自检命令**（在本机跑，最常用）：
```bash
cd dev/blockscout-standalone && source .env
# 测链 RPC
curl -s -X POST "$L2_RPC_HTTP" -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","method":"eth_chainId","params":[],"id":1}'
# 测本机后端
curl -s "http://127.0.0.1:${BLOCKSCOUT_API_PORT}/api/v2/blocks?limit=1" | head -c 200
```

### 9.1 专项：「Internal txns」标签为空

内部交易（合约内部调用 / 转账）由后端**单独的索引器**抓取，区块本身索引正常≠内部交易就有。
排查分两层：**①索引器是不是开着 → ②历史块要不要回填**。

#### 第一步：确认索引器实际是开的（最易踩的坑）

`docker-compose.yml` 里 backend 段的 `environment:` **优先级高于** `env_file:`（即 `envs/backend.env`）。
若有人在 compose 里硬写了一行 `INDEXER_DISABLE_INTERNAL_TRANSACTIONS_FETCHER=true`，
则不管 `envs/backend.env` 写成什么都会被盖掉，内部交易索引器实际是**关的**，全库 0 条。

```bash
cd dev/blockscout-standalone

# 看容器里「实际生效」的值，必须是 false
docker compose exec -T backend env | grep INTERNAL_TRANSACTIONS_FETCHER

# 排查三处定义，确认没有哪里写了 =true
grep -rn 'INTERNAL_TRANSACTIONS_FETCHER' . 2>/dev/null
#   envs/backend.env.tpl  → 应 =false
#   envs/backend.env      → 应 =false
#   docker-compose.yml    → 不该出现这行；若有且 =true 就是它在盖

# 如发现 docker-compose.yml 里被写成 true，改回 false（或删掉该行让其继承 env_file）：
sed -i 's/- INDEXER_DISABLE_INTERNAL_TRANSACTIONS_FETCHER=true/- INDEXER_DISABLE_INTERNAL_TRANSACTIONS_FETCHER=false/' docker-compose.yml
docker compose up -d backend          # 重建 backend 使其生效
```

确认开启后，**新导入的区块**会自动抓内部交易。验证（隔一两分钟跑两次，第二个数应在涨）：
```bash
docker compose exec -T db psql -U blockscout -tAc "select count(*) from internal_transactions;"
```

#### 第二步：回填历史块（索引器曾经关过才需要）

索引器关着期间导入的区块，**不会**自动补内部交易（它们没有进「待处理」队列）。
表现：新块的内部交易有了，但翻看旧交易仍为空。需要把这些历史块重新入队让索引器补抓。

```bash
cd dev/blockscout-standalone

# 1) 先看队列表结构，确认列名（不同版本可能略有差异）
docker compose exec -T db psql -U blockscout -c "\d pending_block_operations"

# 2) 把「有交易、但还没有内部交易」的共识块批量入队（ON CONFLICT 幂等，可重复跑）
docker compose exec -T db psql -U blockscout <<'SQL'
INSERT INTO pending_block_operations (block_hash, block_number, inserted_at, updated_at)
SELECT b.hash, b.number, now(), now()
FROM blocks b
WHERE b.consensus = true
  AND EXISTS     (SELECT 1 FROM transactions t          WHERE t.block_hash = b.hash)
  AND NOT EXISTS (SELECT 1 FROM internal_transactions it WHERE it.block_number = b.number)
  AND NOT EXISTS (SELECT 1 FROM pending_block_operations p WHERE p.block_hash = b.hash)
ON CONFLICT DO NOTHING;
SQL
```

入队后索引器会按 `INDEXER_INTERNAL_TRANSACTIONS_CONCURRENCY`（默认 2）逐批补抓，块多时可能要跑一阵。
进度观察：
```bash
# 剩余待补（应单调下降）
docker compose exec -T db psql -U blockscout -tAc "select count(*) from pending_block_operations;"
# 已入库（应持续上涨）
docker compose exec -T db psql -U blockscout -tAc "select count(*) from internal_transactions;"
```

> 数据量大 / 想省事时，测试环境也可直接 `docker compose down -v && ./install.sh` 全量重灌
> （索引器开着从创世重抓，内部交易自然齐全），代价是整条链重新同步。

#### 日志里这条可忽略

```
GenServer Indexer.Fetcher.OnDemand.FirstTrace terminating
** (ArgumentError) unknown field `:block_hash` in schema Explorer.Chain.InternalTransaction given to insert_all
```
这是 v11.2.0 自编译版「按需补 trace」旁路的已知 bug，**只在打开尚未索引的交易页时偶发，不影响**
主索引器（bulk）正常入库。只要第一/二步做完、`internal_transactions` 在涨，可无视这条报错。

## 10. 应急预案

### 整机/容器全挂
```bash
cd dev/blockscout-standalone
docker compose up -d          # 先尝试拉起
docker compose logs -f backend  # 看是否健康
```
若拉不起来：`docker compose down && ./install.sh`（数据卷保留，不丢索引）。

### 链重建了（chainId 或创世变了）
旧索引数据对不上，必须清库重新索引：
```bash
docker compose down -v        # 清空索引数据
# 确认 .env 里 L2_CHAIN_ID 等已更新成新链的值
./install.sh                  # 从创世重新索引（耗时随链长度增长）
```

### 重新索引（数据错乱但链没变）
同上 `down -v` + `./install.sh`。这是 Blockscout 的「重装大法」，绝大多数数据问题都能解决，
代价是重新同步耗时。
